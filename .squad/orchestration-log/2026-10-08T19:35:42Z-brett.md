## Summary

Agent version created at 18:39:26Z and showed `Status: Running` in portal under a minute — provisioning was healthy. `wait_until_active` polled for 45+ minutes and never terminated. Investigation revealed two independent bugs and one observability failure:

1. **Incomplete enum:** `AgentVersionStatus` missing `running` (also `starting`, `updating` per Brian's production deployer).
2. **Enum stringification bug:** `str(status).lower()` on enum mixin produced `'agentversionstatus.active'` instead of `'active'`. Polling could not have terminated even if service said `active`.
3. **Silent polling:** Loop logged zero status strings. ~270 HTTP 200s with no output about what status was returned. Healthy and hung systems were byte-identical.

**Decisions implemented:**
- Status sets with cited sources: `_READY_STATUSES = {"active", "running"}`, `_PENDING_STATUSES = {"creating", "starting", "updating"}`, `_FAILED_STATUSES = {"failed", "deleting", "deleted"}`.
- Bounded iteration: `for attempt in range(1, attempts + 1)` derived from timeout and poll interval. Loop cannot fail to terminate.
- Every poll logged: agent name, version, verbatim status, attempt `n/N`, elapsed seconds, flushed immediately.
- Unrecognised status warns on every sighting, then raises `UnrecognisedStatusError` at bound.
- Timeouts remain FAILURE. Budget 120s (4x observed ~60s provision time), poll 3s, request timeout 15s, retry 2.
- SDK HTTP logging downgraded to WARNING.

**Primary reference:** `briandenicola/banking-agent-foundry-orchestrator` is a working production deployer for Foundry hosted agents and must be consulted before deriving behaviour from SDK type definitions.

**Tests:** `tests/unit/test_deploy.py` covers ready set, case-insensitivity, enum matching, failure detection, bounded iteration, status logging, and unrecognised-status warnings.
