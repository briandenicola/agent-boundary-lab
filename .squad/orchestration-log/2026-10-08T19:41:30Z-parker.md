## Summary

Hosted-agent runtime pulls the agent image as its own principal (distinct from kubelet identity). `acr.tf` granted `AcrPull` only to AKS kubelet and Container Apps identities. Foundry's `SystemAssigned` principal had no role on the registry.

Without `AcrPull`, an image pull is retryable rather than fatal — the version gets stuck in `creating` and waits indefinitely for an eventually-successful pull that never comes.

**Added:** `azurerm_role_assignment.foundry_acr_pull`
- Role: `AcrPull` (pull only, no push)
- Scope: Registry
- Principal: `azapi_resource.foundry.output.identity.principalId`

**This is a hypothesis, not proof.** Backend pull errors are not readable from outside the private endpoint. The grant is necessary regardless of whether it is sufficient.

**Failure mode (for future debugging):** If version hangs in `creating` again, it indicates missing pull permission. Check this role before re-investigating provisioning time.

**Incidental finding:** `infra/cloud/variables.tf` still defaults `region = "eastus2"`, while live environment is `canadacentral`. A bare `terraform -chdir=./infra/cloud plan` (without Taskfile's `-var region=` override) plans 38 to add and 37 to destroy — full environment replacement including Foundry account and RAI policies. Dangerous default. Recommend change to `canadacentral`, but region is a deliberate choice recorded in A2a; not changed unilaterally.

**For Brett:** `find_matching_version` does not skip `creating`, so a version stuck in that state is reused by the next run. Once this role is granted, a stuck version should recover. Deletion requires a data-plane call from inside the VNet; no SDK surface exists in B9a.
